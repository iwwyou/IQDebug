# 5차 검토 요청: 데이터셋 선정 확정(v5) + 타깃 함수 선정 정책

> 1~4차 외부 검토를 반영해 선정 로직을 네 차례 고쳤다. 지적은 **전수 코퍼스에서 발생 규모를
> 측정한 뒤** 반영했다. 모든 숫자는 2026-10-28, `evaluation/DAppSCAN/select_targets.py`(v5)
> 출력(`targets_v5.json`)과 일치한다. 과거 판은 `historical/select_targets_v{1,3,4}.py` 로 보존.
> **이번에는 선정 로직 검토 + "어떤 함수를 타깃으로 삼을지" 정책 검토를 함께 요청한다.**

## 1. 연구 배경

**Solidity 소스 수준 디버거**를 만들고 있고 ISSTA 2027 제출을 준비 중입니다. 구체 트랜잭션 trace 를
재생하는 디버거가 아니라 **abstract interpretation(구간 도메인)으로 계산한 추상 프로그램 상태 위를
탐색하는 디버거**입니다.

- 타깃 함수를 고르면 엔진이 **디버깅 입력 슬롯**(파라미터·상태변수·`msg.*`/`block.*`·인터페이스 호출
  반환값)을 자동 도출하고 사용자는 값(주로 구간)만 채웁니다. `constant` 는 값이 고정이라 제외됩니다.
- 엔진은 CFG 위 worklist fixpoint 로 **노드마다 추상 환경**을 채웁니다. 내부 호출(internal/상속/
  library/super)은 본문을 해석하고, 인터페이스 외부 호출은 불투명(반환 ⊤)입니다.
- 이후 **디버거 operation(step forward/backward, step into/out, breakpoint, continue)은 엔진을 다시
  호출하지 않고** 계산된 상태 위에서 커서를 움직입니다. 논문의 기여는 이 **operation 들의 의미론**입니다.

RQ: **RQ1** operation 의미론이 실제 코드에서 잘 정의되는가 / **RQ2** operation 응답성과 업데이트
종류별 재사용 / **RQ3** 건전성·정밀도(구체 실행 열거로 γ-포함 검사).

**데이터셋의 역할은 버그 벤치마크가 아니라 "실제 DApp 함수들의 모집단"입니다.** SWC 라벨을 쓰지 않습니다.
"엔진이 그 함수를 분석할 수 있는가"는 **사전 선언한 지원 범위 태깅(B)** 과 **실행 결과 funnel(C)** 로
처리하고 **선정 기준으로 되먹이지 않습니다**.

## 2. 데이터셋 (DAppSCAN)

`InPlusLab/DAppSCAN`(arXiv 2305.08456), `DAppSCAN-source/contracts/<감사회사>-<프로젝트>/<저장소
스냅샷>/...`. 프로젝트 구조가 보존되어 import 폐포를 구성할 수 있고, 실제 감사 대상 코드이며,
선행 연구(심사 중)의 intent 라벨 데이터셋과 겹치지 않습니다.

**빌드 메타데이터는 거의 없습니다** — 21,457개 `.sol` 트리에서 빌드 설정을 가진 디렉터리는 **4곳**
(`package.json` 2, `truffle-config.js` 1, `hardhat.config.js` 1, `package-lock.json` 1). 그래서 remapping
을 읽을 수 없고(보유 스냅샷 0) 패키지 import 는 저장소 안에서 해석되지 않습니다.

## 4. v5 선정 로직 (첨부 `select_targets.py` 가 정본)

1. **수집**: `os.walk(\\?\<root>, onerror=raise, followlinks=False)` + 이름 정렬 + `git ls-files` 대조
   (불일치 시 중단) → **21,457개, 추적 목록과 완전 일치**.
2. **어휘**: `bare`(주석만 공백화, 문자열 유지) / `mask`(주석 + 문자열 내용까지 공백화), 길이·개행 보존.
   pragma·함수는 `mask`(함수는 assembly 블록까지 공백화 → Yul `function` 제외), import 는 키워드를
   `mask` 에서 찾고 경로를 `bare` 에서 읽음(줄 앵커 없음, 전방 길이 제한 없음).
3. **pragma**: semver 제약 → 허용 버전 집합(출시된 solc 0.4.0–0.8.38, 기준일 2026-10-28),
   파일 내 **모든 pragma 의 교집합**. 빈 OR 항·설명 안 되는 토큰·따옴표 섞인 버전은 **거부**(fail-closed).
   채택 조건: 집합이 비지 않고 **최솟값 ≥ 0.8.0**.
4. **경계**: 격리 경계 = 마커를 가진 가장 얕은 조상(깊이≥2), 없으면 `<감사>/<스냅샷>` 2단.
   추정 저장소 루트·판정 방법·**신뢰도**를 별도 기록(경계를 "검증된 저장소 루트" 라고 주장하지 않음).
5. **import 해석(엄격)**: 상대경로 → remappings → 스냅샷 루트 기준 → 같은 디렉터리. 전부 같은 스냅샷
   안이어야 하고 그 외는 미해결. basename·접미사 fallback 없음. 해석마다 method/confidence 기록.
6. **폐포**: 미해결 0 ∧ 모든 파일이 유효 pragma ∧ 전부 ≥0.8 ∧ **공통 컴파일러 버전 존재**.
7. **태그**: 제외 = `external_dependency`(node_modules·`@scope`·알려진 패키지·**스냅샷 루트 직하**의
   lib/vendor/deps), `test_or_mock`(단어 경계), `verification`, `migration`,
   `merged_source`(**원문 `// File:` 마커 ≥2** ∨ flatten 경로명 ∨ **import 0 ∧ 최상위 선언 ≥3 ∧ OZ 본문
   지문 ≥2**). 유지 = `suspected_flattened`, `canonical_names`, `project_lib_dir`.
8. **제외 manifest**: 범용 재사용 프레임워크 저장소(OpenZeppelin 2개, 사유 기록).
9. **산출물**: 모든 파일의 최초 탈락 단계, 근거(`per_file_evidence`), 선정 파일의 import 해석 근거,
   해시 2종(원문/문자열 보존 정규화), 폐포 크기, 특수 함수 집계, 미해결 import 분류와 영향 후보 수.

## 6. 타깃 함수 선정 정책 (이번 검토의 두 번째 주제)

데이터셋이 확정되면 각 파일에서 **어떤 함수를 타깃으로 디버깅할지** 정해야 합니다. 목표는 "컨트랙트
안의 함수가 가급적 모두 커버되는 것"입니다. 제 안은 두 계층입니다.

- **T1 (주 타깃)**: 각 컨트랙트의 **`public`/`external` 구현 함수** = 트랜잭션 진입점.
  호출 그래프 in-degree 0 (= "최상위 호출자")을 기준으로 삼지 않는 이유는, `transfer` 처럼 **내부에서도
  불리지만 진입점인 함수**가 빠지기 때문입니다. 가시성은 선언에 명시되어 있어 판정이 객관적입니다.
- **T2 (커버리지 보충)**: T1 어느 실행에서도 **callee 로 닿지 않은** 구현 함수(internal/private,
  abstract·library 내부 포함)를 직접 타깃으로 추가. 엔진은 임의 함수를 타깃으로 고를 수 있습니다.
- **커버리지 원장**: 함수마다 ① 직접 타깃 ② callee 로 해석됨 ③ **Step Into 로 도달 가능** ④ 미도달+사유.

②와 ③을 나누는 이유는 엔진·UI 의 구조적 한계 때문입니다. **루프 본문 안에서만 호출되는 함수**는
엔진이 해석은 하지만 커서를 루프 본문에 둘 수 없어 **Step Into 로 도달할 수 없습니다**. 즉
**"해석 커버리지"와 "탐색 커버리지"가 다릅니다.** 그 밖에 미커버가 구조적으로 남는 경우:
생성자에서만 호출되는 함수, 외부/인터페이스 호출로만 닿는 함수, 주어진 입력에서 ⊥ 가 된 분기 안의 함수.

마지막 항목 때문에 **커버리지는 입력 자동 채움 정책에 의존**합니다(구간을 넓히면 커버는 늘고 정밀도는
떨어짐). 현재 엔진에는 입력 자동 생성기가 없어(해당 API 가 스텁) 타입 기반 기본값 생성기를 만들어야 합니다.

2. **병합 판정의 잔여 위험**. 본문 지문 30개 문구로 바꾼 뒤 precision 이 올랐지만, ① 자체 구현인데
   OZ 문구만 베껴 쓴 경우(오탐), ② OZ 외 라이브러리(Solmate·DS-Math 등)를 병합한 경우(미탐)가 남습니다.
   지문 목록을 늘리는 것과 AST/바이트 수준 유사도 비교 중 무엇이 비용 대비 효과적일지 판단해 주세요.
3. **타깃 정책(§6)**. T1 을 가시성 기준으로 두는 것이 타당한지, T2 로 커버리지를 메우는 방식이 통계적
   편향을 만들지는 않는지(진입점과 내부 함수가 한 모집단에 섞임), "해석 커버리지 vs 탐색 커버리지"
   구분을 RQ1 의 주요 결과로 제시하는 것이 적절한지 봐 주세요.
4. **입력 자동 채움이 커버리지에 미치는 영향**. 타입 기반 기본값(예: `uint256` → 전 범위, 또는 좁은
   구간)에 따라 feasible 분기 수가 달라집니다. 실험에서 **입력 정책을 변수로 노출**해 민감도를
   보고하는 설계가 맞는지, 아니면 고정 정책 하나로 가야 하는지 의견을 주세요.
5. **AST manifest 범위**. 다음 작업으로 `solc --standard-json` + `stopAfter: "parsing"` 으로
   함수 manifest 를 만들 계획입니다(가시성·kind·구현 여부·소스 범위·내부 호출·상속·루프·분기·
   `unchecked`·inline assembly·modifier·try/catch). 파싱 전용이라 import 해석·타입 검사는 되지 않는데,
   이 범위로 §6 의 T1/T2 판정과 함수 수 확정이 가능한지, 빠진 항목이 있는지 봐 주세요.
6. **ISSTA 리뷰어 관점**. 지금까지의 funnel·태그·근거·민감도 보고 외에 반드시 더 제시해야 할 것이
   있는지 지적해 주세요.

## 8. 답변 형식

① 치명적 결함, ② 개선하면 좋은 것, ③ 타당한 부분 으로 나누고, 각 항목에 구체적 반례나 수정 코드를
붙여 주세요. 데이터셋은 옵션 2 / 2′ / 2′−suspected 중 무엇을 주 집합으로 권하는지, 타깃 정책은 T1 만 /
T1+T2 / 다른 안 중 무엇을 권하는지 분명히 밝혀 주세요.
