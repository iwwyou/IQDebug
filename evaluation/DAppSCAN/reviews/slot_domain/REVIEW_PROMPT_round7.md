# 외부 검토 요청 (라운드 7) — 디버깅 입력 슬롯의 **정의역**을 어디까지 열어야 하는가

작성 2026-10-28. 앞선 라운드는 데이터셋 선정(1~5)과 타깃 계층·입력 정책(6)이었고, 이번은 **엔진
의미론**에 관한 단일 쟁점이다. ISSTA 2027 투고 대상 도구 **IQDebug** 의 설계 결정 하나를 묻는다.

---

## 1. 도구의 구조 (판단에 필요한 최소 배경)

IQDebug 는 Solidity 소스 수준 디버거인데, **구체 트랜잭션 트레이스를 재생하지 않는다.** 구간
도메인(interval) 추상해석으로 함수의 **추상 상태**를 미리 계산해 두고, 사용자는 그 위에서 커서를
움직인다. 논문의 기여는 **디버거 operation 의 의미론**(Step Forward/Backward, Step Into/Out,
Breakpoint, Continue)을 추상 상태 위에서 정의하는 것이다.

호출은 트리거별로 분리돼 있다.

| 호출 | 트리거 | 결과 |
|---|---|---|
| `analyze` | 코드 | CFG 구조 + **빈 debug 슬롯 목록** |
| `evaluate(debug_values)` | 입력 | fixpoint 후 상태가 채워진 CFG (frozen) |
| `verify(intents)` | intent | 보존된 상태 위 standalone 검증 |
| navigation | 사용자 operation | **엔진 호출 0** — 받아 둔 CFG 위 커서 이동 |

**슬롯(slot)** = 사용자가 값을 채워야 하는 칸. 엔진이 코드에서 **도출**하고(사용자가 만들지 않는다),
사용자는 값만 넣는다. 4종이다.

| 종류 | 예 | 의미 |
|---|---|---|
| `@Param` | `amount` | 타깃 함수의 파라미터 |
| `@StateVar` | `totalSupply`, `poolInfo[1].amount` | 컨트랙트 상태변수(진입 시점 값) |
| `@GlobalVar` | `msg.sender`, `block.timestamp` | 정적 화이트리스트 |
| `@IReturn` | `oracle.price()` | 본문 없는 **인터페이스 호출의 반환값** |

값은 `[lo,hi]` 구간 / `symbolicAddress N` / `true|false|any` 등으로 준다. **입력은 "타깃 함수 진입
시점" 의 값**이라는 것이 설계 전제다 — 단일 트랜잭션 안에서 그 함수를 실행하는 상황을 추상적으로
세운다.

별도로 **intent**(`@During`/`@Post`)가 있다. 이것은 코드의 영구 일부로 작성하는 명세이고, 보존된
추상 상태 위에서 검증된다. 슬롯과는 다른 개념이다(슬롯 = 입력, intent = 명세).

## 2. 쟁점

### 2.1 현재 구현

`engine_api._derive_debug_slots` 는 상태변수 후보를 **상속까지 포함해** 전부 모은 다음
(`_all_state_vars(ccf, contract_cfgs)`, `constant` 제외), 마지막에 **참조 여부로 걸러낸다**:

```python
# engine_api.py:1422-1431
for name, var in statevars.items():
    if name in compound_roots and not isinstance(var, StructVariable) and \
            getattr(getattr(var, "typeInfo", None), "typeCategory", None) in ("mapping", "array"):
        continue
    if not (name in scalars or (func_src and _referenced(name, func_src))):
        continue                      # ← 이 줄이 쟁점이다
    ...
    add("StateVar", name, _valuekind_of(...))
```

`scalars` 는 **타깃 본문 + footprint**(내부 호출·modifier·라이브러리·`super`/`this` 로 이어지는 함수들)를
훑어 모은 참조 집합이고, `func_src` 는 타깃 함수 소스 텍스트에 대한 단어 경계 검사다.

즉 **타깃 함수(와 그 footprint)가 읽거나 쓰는 상태변수만 슬롯이 된다.** 그 함수가 손대지 않는
상태변수에는 칸이 생기지 않는다.

intent 는 이 필터를 우회하는 경로가 있다 — `_derive_debug_slots(..., intent_texts=[...])` 로 intent
텍스트를 받아 거기서 참조된 이름도 `scalars` 에 넣는다(`engine_api.py:1361`). 즉 **intent 를 쓰면
미참조 상태변수에도 슬롯이 생기지만, intent 가 없으면 생기지 않는다.**

### 2.2 도구 저자의 문제 제기

> intent 는 함수에서 안 쓰이는 상태변수도 참조해야 한다. **함수가 건드렸어야 하는데 안 건드린
> 상태변수**를 겨냥한 intent 가 실제로 있었다. 그러면 디버깅 입력은 함수에서 쓰이는 것만 주는 게
> 맞는가, 아니면 입력도 똑같이 열어야 하는가?

구체적으로 문제가 되는 상황은 이렇다. `withdraw()` 가 `balance` 를 줄이면서 `totalDeposits` 를
갱신하는 것을 **잊었다**고 하자. `@Post totalDeposits(EXIT) == totalDeposits(ENTRY) - amount` 같은
intent 로 이 누락을 잡고 싶다. 그런데 `totalDeposits` 는 함수 본문에 등장하지 않으므로
(intent 를 쓰지 않는 한) **진입값을 지정할 칸이 없다.** 값이 없으면 ⊤ 로 시작하고,
`⊤ == ⊤ - amount` 는 판정이 무의미해진다.

### 2.3 반대쪽 비용

그렇다고 "미참조도 전부 슬롯" 으로 열면:

- 사용자가 채워야 하는 **칸 수가 늘어난다**. 이 도구는 "여러 입력의 수행 상황을 한 번에 본다" 는 것이
  장점인데, 칸이 많아지면 입력 자체를 세우는 비용이 올라간다(논문의 비용 지표 중 하나).
- **입력 공간이 커진다**. 슬롯마다 구간을 주면 상태공간이 곱으로 늘고 fixpoint 비용이 올라간다.
- `@GlobalVar` 는 더 심하다. 화이트리스트가 **정적**이라 "미참조도 슬롯" 원칙을 그대로 적용하면
  **모든 타깃 함수에 모든 글로벌이 붙는다**(`block.timestamp`, `block.number`, `msg.value`, …).
  이건 명백히 과하다 → 원칙에 경계가 필요하다는 신호다.
- 추상해석 관점에서, 함수가 읽지 않는 변수의 진입값은 **그 함수의 출력에 영향이 없다**. 영향이 없는
  변수에 입력을 받는 것이 의미가 있는가? (intent 검증에는 의미가 있다 — 판정의 기준점이 되므로.)

## 3. 실측 (DAppSCAN 기반 데이터셋, AST 하한)

데이터셋: DAppSCAN 의 감사 대상 소스 중 사전 조건(Solidity ≥0.8, 스냅샷 내 의존성 폐포, flattened·
테스트·mock 제외)을 만족하는 **569 파일 / 101 스냅샷 / 95 감사 프로젝트**.
타깃 = ABI-visible contract function 중 본문에 호출·분기·루프가 있는 것 = **1,941개**
(중복 파일 제거 후 1,900).

수치 입력(구간을 줄 수 있는 `u?int*` 스칼라) 출처를 두 규칙으로 센 결과:

| 출처 | 참조 규칙 (현재 구현) | 전체 규칙 (미참조 포함) |
|---|---|---|
| 파라미터에 정수 스칼라 | 957 | 957 |
| 상태변수에 정수 스칼라 | **323** | **1,032** |
| 수치 글로벌 참조 | 217 | (화이트리스트가 정적이라 전부) |
| 인터페이스 호출 후보(@IReturn) | 528 | 528 |
| **수치 입력이 하나라도 있는 타깃** | **1,152 (59%)** | **1,419 (73%)** |
| 슬롯이 하나도 없는 타깃 | 594 (31%) | 391 (20%) |

> 측정 주의: AST parse-only 라 **상속받은 상태변수는 보이지 않는다**(두 숫자 모두 하한이다).
> 또 `stateVariable` 플래그는 parse-only 에서 **항상 False** 로 들어오므로 구조 위치로 판정했다.
> 정확한 값은 엔진의 `_derive_debug_slots` 를 실제로 돌려야 나온다(아직 안 돌렸다).

핵심은 **상태변수가 323 → 1,032 로 3배**가 된다는 점이다. 수치 입력을 가진 타깃 비율이
59% → 73% 로 올라가는 대신, 칸 수가 늘어난다. 칸 수를 직접 세면:

| | 참조 규칙 | 전체 규칙 |
|---|---|---|
| 수치 슬롯 **총 칸 수**(1,941 타깃 합계) | **2,119** | **6,175** |
| 타깃당 평균 | 1.09 | **3.18** |

즉 커버리지 +14%p(59%→73%) 를 얻는 대가로 **채울 칸이 2.9배**가 된다. 이 교환이 받아들일 만한지가
질문 5의 핵심이다.

## 4. 묻고 싶은 것

1. **슬롯의 정의역을 "타깃 함수가 참조하는 것" 으로 제한하는 것이 추상해석 기반 디버거에서 옳은
   선택인가?** 다른 도구(심볼릭 실행기, concolic, 불변식 검사기)는 초기 상태의 정의역을 어떻게
   정하는지, 그 관례에 비추어 평가해 달라.

2. **입력(슬롯)과 명세(intent)의 정의역이 달라도 되는가?** 즉 "intent 는 모든 상태변수를 참조할 수
   있지만 입력은 참조된 것만 줄 수 있다" 는 비대칭이 정당한가, 아니면 §2.2 의 누락 탐지 사례처럼
   비대칭 때문에 **기능이 성립하지 않는 경우**가 생기므로 통일해야 하는가?
   (현재 구현은 intent 가 있으면 자동으로 열리는 **하이브리드**인데, 이 하이브리드 자체가
   "입력 가능한 칸이 intent 유무에 따라 달라진다" 는 예측 불가능성을 만든다 — 이 점도 평가해 달라.)

3. **읽지 않는 변수의 진입값을 받는 것이 의미가 있는가?** 그 함수의 출력에는 영향이 없지만 intent
   판정의 기준점이 된다. 이 둘을 구분해 "입력 슬롯" 과 "참조점(reference point)" 을 **다른 개념으로
   분리**하는 설계가 더 나은가?

4. **중간 설계안들**을 평가해 달라. 저자가 떠올린 것은 다음인데, 더 나은 안이 있으면 제시해 달라.
   - (A) 현행 유지 + intent 경로만 공식화 (문서에 "intent 가 슬롯을 연다" 를 명시)
   - (B) 상태변수는 전부 열고, 글로벌은 참조된 것만 (타입별로 규칙을 달리)
   - (C) 전부 열되 UI·생성기에서 **참조된 것을 우선 노출**하고 미참조는 접어 둔다(정의역은 넓고 기본
     노출은 좁다)
   - (D) 전부 열되 미참조 슬롯은 **`@Post` intent 가 참조할 때만** 활성화 (현행의 명시적 버전)
   - (E) 입력은 참조된 것만, intent 는 미참조도 참조 가능하되 **그 경우 진입값을 심볼릭 상수로
     고정**(값을 묻지 않고 "변하지 않았다" 만 판정 가능하게)

5. **실험 설계에 주는 영향.** 논문의 RQ1 은 "의미론이 실제 코드에서 잘 정의되는가"(착지점 커버리지,
   breakpoint 가능 비율, Step Into 가능 비율 등)이고, 비용 지표로 **사용자가 채워야 하는 칸 수**를
   쓴다. 정의역을 넓히면 커버리지(수치 입력을 세울 수 있는 타깃 비율)는 올라가고 비용은 올라간다.
   이 트레이드오프를 논문에서 **어떻게 보고**해야 공정한가? 한 설정만 고르는 것보다 두 설정을 모두
   보고하는 것이 맞는가?

6. **위협(threats to validity)** 으로 적어야 할 것은 무엇인가? 특히 "입력 정의역을 좁게 잡아서
   커버리지가 낮게 나왔다" 또는 "넓게 잡아서 비용이 과대평가됐다" 는 지적을 어떻게 선제 차단하는가?

## 5. 답변에 바라는 형식

- 추측과 확인된 사실을 구분해 달라. 우리 코드를 보지 않고 추정한 부분은 그렇다고 표시해 달라.
- 우리가 **틀렸다고 보는 지점**이 있으면 근거와 함께 분명히 적어 달라. 동조하는 답변은 쓸모가 없다.
- 설계안을 고르라면 하나를 고르고 **왜 나머지를 버리는지**까지 적어 달라.
- 우리가 측정해야 할 숫자를 제안한다면, **어떤 결정이 그 숫자에 달려 있는지**까지 함께 적어 달라.
