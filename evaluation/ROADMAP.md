## 구현 계획 — 타입·storage 참조·값 슬롯 (2026-11-24~, 구현 세션)

논의 경위는 대화에서 사용자와 합의한 것이다. 단계마다 승인 후 진행하고 결과를 보고한다(코어 수정).

### 결정된 것

1. **solc 게이트.** 컴파일되지 않는 소스는 해석하지 않는다(`solc_gate.py`, `analyze_source`·`update` 앞단). 415 파일 전부 통과, 중앙값 0.04 초.
2. **슬롯.** 기본 슬롯 = 파라미터·전역값·일반 상태변수. 지역변수는 디버깅 입력이 아니다. keccak256 은 계산하지 않는다(⊤).
3. **mapping.** mapping 마다 **변수 방식**(`m[x]`, 코드에 적힌 대로, 지금 가리키는 칸을 옆에 표시)과 **값 방식**(사용자가 `m[3]`, `m[4]` 를
   추가) 중 하나를 고른다. 변수 방식은 index 가 함수 시작 값 그대로일 때만. 추가하지 않은 칸은 ⊤. 겹치는 입력은 기존 모순 검사가 처리한다.
4. **동적 배열.** 사용자가 0 번부터 원소를 추가한다. 추가한 수 = 길이, 기본 0, 범위 밖 접근은 revert. 배열 index 는 변수 슬롯을 두지 않는다.
   정적 배열은 길이만큼 슬롯. "배열만 빈 값이 기본" 은 논문에 명시하고, 입력 생성기는 원소를 채워야 한다.
5. **자동 슬롯 추천은 하지 않는다**(위 3·4 의 추가 방식으로 대체). 슬롯 발견률은 지표로 쓰지 않는다.
6. **storage 참조 = 위치(화살표).** 묶일 때 위치를 정한다. 같은 참조가 분기마다 다른 곳을 가리키면 join = 후보 모음({a, b}).
   후보가 하나면 strong update, 여럿이면 각 후보가 "옛 값 또는 새 값"(기존 index 규칙과 같다, path-insensitive).
   같은 배열의 후보(`poolInfo[1]`·`poolInfo[2]`)는 index 를 구간으로 합친다.
7. **memory 별칭.** memory → memory 대입·인자·반환은 화살표 복사, storage·calldata → memory 는 새 객체, 루프 안 `new` 는 하나로 합쳐
   weak update. 타깃 함수의 memory 파라미터는 서로 다른 객체로 가정한다(가정으로 명시).
8. **storage 파라미터 함수(117).** 타깃에 유지한다. 단독 실행에서는 파라미터가 가리킬 곳을 디버깅 입력으로 받는다(기본 = 별도 칸,
   후보 = 같은 타입의 상태변수 칸·앞선 같은 타입 파라미터). RewardsManager `_deposit/_withdraw` 는 호출부대로 `poolInfo[pid]`.
9. **이름이 같은 선언.** 참조는 이름 글자가 아니라 **어느 선언인지**로 기억한다(파라미터 g 와 상태변수 g).
10. **대상 함수 범위.** 전부 타깃(§0.2-7 유지), `is_root` 부분집합은 보조.

`'AccessControl is Context'` 5, `using SafeCast` 2 …). 즉 이 측정은 **E1c 이전의 하한**이고,
E1c(레지스트리 빌드) 후 재측정해야 한다.

의존성과 무관한 나머지 원인(작다): `NotImplementedError / Unhandled expression context` 5,
`UnsupportedShadowing` 6(문서화된 한계), `ValueError / Contract context not found for line N` 다수.

### F1 — RQ1 (의미론이 실제 코드에서 잘 정의되는가)

착지점 커버리지 + 누락 원인 분포(루프 본문/더미/접힌 join/sink) · breakpoint 가능 줄 비율 + 거부 사유 ·
Step Into 가능 vs opaque 사유 분포 + **A-D8 로 도달 불가한 비율** · frontier 크기 분포 ·
불변식 위반 0건 확인 · ⊥ 노드·줄 비율 · **루프 탈출 경로 분포**(normal·break·return·revert, infeasible 비율 — K3 의 효용)

### F2 — RQ2 (재사용과 응답성)

operation 별 응답 시간(엔진 호출 0 주장의 실측) · `evaluate` 시간 vs 상태공간 크기 ·
`update` 수술 종류별 분해 · 업데이트 3분류 재계산 경계 + 커서·스택 보존 검증 · baseline 비교(재관찰 A/B/C, §0.1-12·§0.2-4)

### F3 — RQ3 (soundness·정밀도)

γ-포함 검사 · 도달성 판정 검사(거짓 unreachable / 정밀도 손실) ·
상태공간 확대 효과 · loop delta soundness · 지표·표본·보고 구분은 §0.2-3·§0.2-5

### F4 — 이월된 개별 측정

한 줄 다중 호출 **21.7%**(완료) · merge-source 검증 · micro·macro 재가중

## 참고: §0 상세 경위 (2026-11-16~17 논의 기록)

현행 요약은 §0. 아래는 각 결정의 배경·대안·근거·사용자 의견을 논의 당시 형태로 남긴 것이다. 요약과 다르면 요약이 우선한다.

### 0.1 결정된 것

1. **비교군 = W1·W2·W3b.** W1 = forge 테스트 + `forge test --debug`. W2 = `anvil` + `forge create` +
   `cast call --trace --debug --with-local-artifacts --override-state-diff`. W3b = Hardhat 3 `console.log` 계측 사본(상태는
   `hardhat_setStorageAt`). W3a 는 제외, W4(standalone SolDB)는 비교군이 아니라 계측 도구.
2. **공통 소스 = 정규화 소스.** 세 도구 모두 `normalize_source.py` 출력을 컴파일·분석한다(줄 좌표 통일). 도구별 입력
   (forge 테스트, cast 명령열, Hardhat 스크립트, IQDebug 입력 JSON)은 **정본 케이스 하나에서 생성**하고 손으로 고치지 않는다.
3. **IQDebug 가 도출한 슬롯은 전부 구체값으로 채운다** — baseline 과 같은 상태에서 출발. 끝내 못 채운 슬롯이 있는 케이스는 표시해 따로 집계.
4. **range 는 정수 구간만**, 파라미터와 정수 상태변수 모두에 허용. 주소·bool 은 구체값 하나.
5. **루프 본문 안 지점은 IQDebug 에서 무조건 "관찰 불가"** 로 집계(설계 결정의 대가를 정직하게 보고).
6. **정본 케이스 규칙**: 주소는 별칭(`sender`, `owner`, `a1`) + 별칭 ↔ hex ↔ 기호 id 대응표(같음/다름 관계 보존) · 상태 경로 문법 고정
   (`이름`, `이름[키]`, `이름.필드`) · revert 케이스는 IQDebug 에서 "ERROR 로 가는 분기가 feasible 한가" 로 판정, 사후 상태 비교는
   `return` 케이스만 · constructor 는 baseline 이 `ctor_args` 로 배포한 직후 storage 를 덤프해 공통 초기 상태로 쓴다.
7. **데이터셋 = IQDebug 와 baseline 의 공통 데이터셋.** 포함 여부는 도구 중립 기준(정규화 소스 + import 폐포가 지정 solc 로 **컴파일**)으로만
   정한다. solc = pragma 가 허용하는 설치 가능한 최대 버전(DAppSCAN 에 build-info 가 없어 원 설정 복원 불가).
   **2026-11-17 확정: 보완 규칙(버전 내리기, optimizer 켜기)은 두지 않는다.** 이 버전과 optimizer off 로 컴파일되면 넣고, 안 되면 뺀다.
8. **IQDebug 의 지원 범위 안 실패는 버그로 보고 고쳐서 포함한다.** 도구 실패로 데이터셋에서 빼지 않는다. 분모는 타깃 486 중 대상 함수가
   없는 4 파일(stub 3 + 원본 자체가 컴파일 불가 1)을 뺀 **482 파일** → **2026-11-17 정정: 480 파일.** §0.1-7 의 컴파일 기준으로 Compound cToken·eden
   governance 2 개가 더 빠진다(§0.3-6). 486 전부를 평가 대상으로 다루고, 빠진 6 개는 사유와 함께 보고한다(stub 3, 원본 컴파일 불가 1, 정책 버전 컴파일 불가 2). "폐포 전체 Complete 397 / 나머지 89" 는 **파일 단위의 엄격한 지표**
   (의존 파일 하나만 실패해도 그 타깃 전체를 실패로 셈)이지 평가 대상을 397 로 줄인다는 뜻이 아니다. 89 는 원인 분류 완료(엔진 한계 I5·I7 +
   파이프라인 BOM).
9. **`this.f()` 호출 문맥 수정 (2026-11-16, 코어 `Interpreter/Engine.py`).** callee 프레임에서 `msg.sender = address(this)`,
   `msg.value = 0`, 복귀하면 호출자의 `msg.*` 그대로(되쓰기 차단). 예전엔 호출자의 `msg.sender` 를 그대로 써서
   `require(msg.sender == address(this))` 가 ⊥(거짓 unreachable), 반대로 소유자 검사는 거짓 reachable 이었다. 남은 한계:
   `this.f{value: x}()` 의 값 전달 미지원(0). 타깃 486 중 `this.f()` 는 4 파일 5 회. 회귀 스크립트 전부 통과(T8 기존 실패 제외). 미커밋.
10. **정규화 전후 의미 일치는 우선순위가 낮다.** 같은 소스로 세 도구를 비교하므로 비교의 내적 타당성 문제가 아니다. 외적 타당성
    ("실제 DAppSCAN 컨트랙트") 확인용으로 `verify_normalize.py`(`bytecodeHash = none`, optimizer off, creation·deployed 비교) 를
    전체에 한 번 돌려 결과를 보고한다. → **2026-11-17 전수 결과: 컴파일된 483 타깃 모두 원본과 정규화본의 creation·deployed 바이트코드가
    컨트랙트 전부에서 같다**(§0.3-6).
11. **외부 호출 모델링 범위는 철저히 조사해 논문에 명시한다.** 단위는 타깃 함수의 visibility 가 아니라 **호출 지점의 종류**:
    - CG1 완전 실행(Step Into 가능): 내부, 상속, 부모 이름 지정, virtual 최하위·`super`, library, `this.f()`
    - CG2 반환값 입력(IReturn): 인터페이스 view/pure
    - CG3 효과 미모델링(반환값 ⊤, 피호출 쪽 상태·재진입 미모델링): 상태 변경 인터페이스 호출, 컨트랙트 타입 변수 외부 호출,
      `call`/`delegatecall`/`staticcall`, `transfer`/`send`
    - CG4 미지원: 파일 수준 free function
    - **2026-11-17 전수 집계**(§0.3-6): CG4 는 486 폐포 어디에도 없다(0). 그래서 free function 은 구현하지 않는다.
    - **분류 정정(2026-11-17).** view 외부 호출은 0.5 부터 STATICCALL 로 컴파일돼 피호출 쪽이 상태를 바꿀 수 없다. 재진입으로 우리 storage 가
      바뀔 일도 없다. 그래서 **컨트랙트 타입 변수의 view 호출은 CG3 가 아니다.** 효과는 안전하고 반환값만 ⊤ 다. 코드가 폐포에 있어도 그 본문을
      실행하지 않는다. 주소 `a` 에 있는 인스턴스의 storage 가 입력에 없어 결과가 대개 ⊤ 이고, 런타임 타입이 override 한 하위 컨트랙트일 수도 있다.
      IReturn 슬롯은 정밀도 개선용 선택 사항이다. 사용자 판단으로 지금 다시 세지는 않는다. CG3 수를 논문에 낼 때(대상 동결 시) 정정 기준으로 다시 센다.
12. **재관찰 비교의 전제**: W1·W2 도 trace 재생이라 **같은 입력 안에서는 step backward 포함 재실행이 없다.** "evaluate 후 탐색에 엔진
    재실행이 없다" 는 IQDebug 만의 장점이 아니다. 차이는 입력 집합(구간 하나 vs 구체 입력 하나씩)과 경로 전환(다른 분기를 보려면
    그 분기를 타는 입력이 필요)이다. W3b 는 stepping 이 없어 매번 재실행.
13. **분기·루프가 없어도 의미 있는 연산이 있는 함수는 포함한다.** 문장마다 연산 하나뿐인 함수(`balances[msg.sender] += amount;
    total += amount;`)는 상세 비교에서 뺀다. 기준은 0.2-2.

### 0.2 세부 결정과 그 경위

각 항목은 **배경**(왜 이 문제가 나왔나) → **현재 안** → **근거** → **남은 쟁점** 순서로 적는다.
2026-11-17 현재 0.2-1·0.2-2·0.2-3·0.2-4·0.2-7 은 확정되었고(각 항목의 "확정"·"사용자 의견" 줄), 0.2-5 는 논문 작성 때, 0.2-6 은 측정 단계에서 다룬다.
남은 작은 세부(0.2-1 판정 기준, 0.2-2 문장 계수 규칙, 0.2-7 root 판별 범위)는 구현할 때 정해서 기록한다.

#### 0.2-1 분모 구조 (무엇을 몇 개 중에서 셀 것인가)

- **배경.** 1차 외부 검토(P0-1)의 지적. 예: 1,000 케이스 중 IQDebug 600 성공, forge 950 성공, 둘 다 성공 580 이라면, 580 개로만 시간을
  비교할 때 IQDebug 가 실패한 (아마 더 어려운) 400 개가 성능 분석에서 조용히 사라진다. 580 개 위의 시간 결과를 "IQDebug 의 전체 성능" 처럼
  쓰면 선택 편향이 된다. 기존 계획에는 "공통 성공 집합 위 쌍체 비교" 한 줄만 있었다.
- **현재 안.** 네 집합을 따로 정의하고 각각 다른 용도로 쓴다.
  - D0 = 도구 중립 자격(컴파일 + 대상 함수 규칙)을 만족한 전체 케이스. → 전체 지원률·실패율의 분모.
  - D1 = IQDebug 가 케이스가 지정한 관찰을 내준 케이스. → IQDebug 관찰 가능률.
  - D2-W = baseline W(W1·W2·W3b 각각)가 지정한 관찰을 내준 케이스. → baseline 별 관찰 가능률.
  - D3-W = IQDebug 와 W 가 **둘 다** 같은 관찰 목표를 달성한 케이스. → 시간 쌍체 비교. W 마다 다른 집합이다.
  - D3-W 위의 시간은 "양쪽이 성공한 경우의 조건부 성능" 이라고 명시한다. timeout 은 누락시키지 않고 별도 실패 유형으로 센다.
- **근거.** 사용자 방침(§0.1-8)이 "지원 범위 안의 실패는 고쳐서 포함" 이므로, 고쳐 갈수록 D0 와 D1 의 차이는 **지원 범위 밖**(CG4 free function,
  수술 미지원 편집, 루프 본문 관찰 등)만 남는다. 그래도 실패가 0 이 되지는 않고 baseline 쪽 실패(하네스 생성, private 직접 호출 불가)도 있으므로
  분모 구분은 필요하다.
- **남은 쟁점.** "관찰을 내줬다" 의 판정 기준(값 하나라도 / 지정 변수 전부)과, 부분 성공 케이스의 처리.
- **사용자 의견(11-17).** IQDebug 와 baseline 은 **같은 정본 케이스**로 진행한다. free function 은 구현이 필요하면 구현하는데, 전수 집계상 0 이라
  필요 없다. 루프 본문 관찰은 지원하지 않는다(§0.1-5, 관찰 불가로 집계). → 분모 구조는 사실상 확정. 판정 기준과 부분 성공 처리만 남았다.

#### 0.2-2 연산 계층 기준 (분기·루프가 없는 함수 중 무엇을 넣을까)

- **배경.** 실질 타깃 규칙(DATASET_RECORD §8)은 "builtin 이 아닌 호출 ∨ 분기 ∨ 루프" 가 있는 함수만 넣는다. 외부 검토(3.2절)는 이게 직선형 함수를
  통째로 빼는 편향이라고 지적했다. 사용자 판단: 정수 연산이 있는 함수는 여러 입력을 구간으로 넣었을 때의 추상 해석 결과 자체가 의미가 있으므로
  넣어야 한다. 다만 `balances[msg.sender] += amount; total += amount;` 같은 함수는 결과가 "입력 구간을 한 번 옮긴 것" 이라 굳이 볼 필요가 없다.
  문제는 **사소한 것과 의미 있는 것을 객관적으로 어떻게 가르나**이다.
- **현재 안.** 분기·루프·호출이 없는 함수 중 아래 하나라도 해당하면 "연산 계층" 으로 넣는다(내부 callee 까지 펼친 뒤 판정).
  - (a) **연산 합성**: 한 식 안에 산술 연산자가 둘 이상 중첩. 예: `a * b / c`, `x + y - z`. 사용자가 말한 "한 줄에 add·sub·mul 을 복합적으로" 에 해당.
  - (b) **비선형 연산**: `*` `/` `%` `**` 시프트가 있고 피연산자가 **둘 다** 입력(파라미터·상태변수)에 의존. 예: `a * b`. 줄이 짧아도 구간 결과를
    손으로 짐작하기 어려워지는 지점이다.
  - `deposit` 예시는 문장마다 연산이 하나이고 선형이라 둘 다 해당하지 않아 빠진다.
  - 어느 계층에도 들지 않는 함수는 상세 비교에서 빼고 analyze 성공률만 보조로 집계한다(비용이 작음).
- **근거.** 결과를 본 뒤 기준을 정하면 "도구에 유리한 함수만 골랐다" 는 의심을 받는다. 그래서 **AST 만으로 판정하고 엔진 실행 전에 고정**한다.
- **남은 쟁점.** ⚑ (1) 0.8 의 checked arithmetic 때문에 `+=` 하나도 overflow revert 가능성이라는 관찰 대상이 있다. 범위만 주면 거의 항상
  "가능" 이라 정보가 적어 기준에서 빼자는 것이 제안이다. (2) 데이터 의존 깊이·서로 다른 입력 수 같은 다른 기준이 더 나은지는 외부 검토 중.
- **사용자 의견(11-17).** 기준을 **statement 수 ≥ 3**(함수가 쓰는 modifier 의 문장은 제외)으로 하자는 제안. 단순하고 AST 로 기계적으로 판정되며,
  엔진 실행 전에 고정할 수 있다는 장점이 있다.
  - *이 세션 검토.* 문장 수만 쓰면 길이를 재게 된다. `deposit` 류에 대입이 하나 더 붙으면 들어오고, `return a * b / c;` 같은 한 줄 비선형 함수는 빠진다.
    그래서 문장 수와 연산 조건을 합친다.
  - **확정(11-17, 이 세션 제안에 사용자 동의).** 분기·루프·호출이 없는 함수는 아래 둘 중 하나를 만족하면 연산 계층으로 넣는다.
    - (A) **statement 3 개 이상**(modifier 문장과 `emit` 은 제외) **이면서** 입력(파라미터·상태변수)에 의존하는 산술 연산이 하나 이상 있다.
    - (B) 한 식 안에 산술 연산자가 2 개 이상 있다(위 (a)). 또는 두 입력에 함께 의존하는 비선형 연산이 있다(위 (b)).
    - AST 만으로 판정하고 엔진 실행 전에 고정한다. 동결할 때 함께 정할 세부는 셋이다. 내부 callee 를 펼친 뒤 셀지. 선언문·`require` 를 문장으로 칠지.
      checked arithmetic 의 overflow 가능성만 있는 경우(위 (1))를 제외할지. 정해지면 `target_functions.json` 동결로 넘어간다(§0.3-6).

#### 0.2-3 표본 추출 (soundness 검사에 구체 입력을 몇 개, 어떻게 뽑나)

- **배경.** 범위 실험은 IQDebug 에 구간 하나를 주고, baseline 으로 그 구간 안의 구체 입력들을 실행해 "구체 결과가 IQDebug 구간에 들어가는가" 를 본다.
  기존 계획은 N 사다리(100/1,000/10,000)였다. 사용자 지적: N=10,000 이 아니라 **변수마다 5 개씩만 잡아도** 조합 수가 크게 늘어난다.
  실제로 조합 수는 5^k 이고 변수 6 개면 15,625 다.
- **현재 안.** 변수별 개수가 아니라 **케이스당 총 예산 N** 을 고정한다.
  - 전체 조합 수가 N 이하이면 전수 실행한다. 이 경우에만 "전수 검증" 이라고 쓴다.
  - N 을 넘으면 다음 순서로 채운다. ① 모든 변수가 하한인 것 1 개와 모든 변수가 상한인 것 1 개. ② 한 변수씩만 경계값(하한, 하한+1, 중간,
    상한−1, 상한)으로 바꾸고 나머지는 중간값(변수 k 개면 5k 개, 변수 수에 **선형**). ③ 남은 예산은 고정 시드 무작위.
  - N 을 늘릴 때 작은 표본이 큰 표본에 포함되게 한다(N=100 결과가 N=1,000 결과의 부분집합).
- **근거.** 표본은 **자동 soundness 검사용**이다. 사용자 시간 측정과 무관하고, IQDebug 결과(구간 하나로 한 번 계산)에도 영향이 없다. 비용은 baseline
  실행 시간 × N 뿐이다.
- **남은 쟁점.** ⚑ ② 는 변수 하나씩만 움직이므로 `a - b` underflow 처럼 **두 변수를 함께** 봐야 드러나는 경우를 놓칠 수 있다. pairwise covering array
  (모든 변수 쌍의 경계값 조합을 최소 개수로 덮는 표본)를 쓸지. N 값 자체는 0.3-3.
- **사용자 의견(11-17).** 변수별로 범위를 다르게 잡지 않고 모든 변수에 같은 폭을 준다. 폭을 1..5(또는 1..10)로 올리며 baseline 은 전수 열거한다.
  세부와 baseline 시간 산정 방식은 §0.3-3 의 "2026-11-17 논의 결과".
- **확정(11-17).** IQDebug 에는 모든 입력을 구간으로 준다. baseline 은 그 구간의 조합을 **전수 열거**해 soundness 정답을 만든다.
  위 ②(경계값 표본)·pairwise covering array 는 조합을 **표본으로** 뽑을 때만 필요한데, 이제 표본을 뽑지 않으므로 필요 없다.
  - *조건.* 이 결론은 soundness 검사를 **조합 수가 전수 상한(10^4 안) 이하인 설정에서만** 한다는 전제 위에 선다. 예를 들어 변수당 값이 10 개면 변수 5 개부터(10^5),
    5 개면 6 개부터(5^6 = 15,625) 상한을 넘는다. 상한을 넘는 설정은 비용(외삽)만 보고하고 soundness 검사는 하지 않는다. 그래서 변수가 많은 함수는 작은 w 에서만 검사된다.
    이 점은 한계로 적는다.

#### 0.2-4 재관찰 3 분류와 witness 입력

- **배경.** 외부 검토는 "evaluate 이후 탐색이 엔진을 재실행하지 않는 것이 IQDebug 의 핵심 장점" 이라고 했다. 사용자 반론: forge 디버거는 step backward 를
  지원하므로 forge 도 실행 후 탐색에 재실행이 필요 없다. 차이는 여러 입력을 한 번에 보여 주느냐, 입력마다 다시 돌려야 하느냐이다. 확인 결과 W1·W2 는
  한 번 실행한 trace 를 재생하는 방식이라 사용자 반론이 맞다. W3b(`console.log`)는 stepping 이 없어 다시 보려면 재실행이다.
- **현재 안.** "다시 보기" 를 세 상황으로 나눠 따로 잰다.
  - A. **같은 입력·같은 경로를 다시 보기.** IQDebug·W1·W2 모두 재실행 없음. W3b 만 재실행. 여기서는 IQDebug 의 이점이 없다고 정직하게 보고.
  - B. **다른 경로 또는 다른 입력을 보기.** 예: 어떤 `if` 에서 지금 안 탄 쪽을 보고 싶다. IQDebug 는 그 분기가 주어진 구간에서 feasible 이면 탐색만으로
    넘어간다. baseline 은 그 분기를 타는 **구체 입력(witness)** 을 찾아서 다시 실행해야 한다.
  - C. **소스 편집 후 다시 보기.** IQDebug 는 증분 update(수술 종류별), baseline 은 재컴파일·재실행. IQDebug 의 수술 미지원 편집은 IQDebug 실패.
  - B 에서 witness 를 찾는 시간(SMT·퍼저)까지 baseline 시간에 넣으면 디버거가 아니라 입력 생성 도구를 평가하게 된다. 그래서 **witness 를 정본
    케이스에 미리 넣고** baseline 은 그 입력으로 재실행하는 시간만 잰다(baseline 에 유리한 보수적 비교).
- **근거.** witness 를 주면 B 의 baseline 비용은 "한 번 더 실행"(W2 기준 1 초 미만)이라 시간 차이는 작게 나올 가능성이 크다. 그래서 B 의 주장은 시간이
  아니라 **"IQDebug 는 witness 없이 경로를 바꾼다"** 로 옮기고, 그 근거로 정본 생성 때 자동 탐색이 **witness 를 찾지 못한 분기의 수·비율**을 보고한다.
  그 분기는 baseline 으로는 볼 수 없었던 경로다(동시에 IQDebug 의 feasible 판정이 구체적으로 확인되지 않은 경로이기도 하다).
- **남은 쟁점.** ⚑ witness 탐색 방법(누가, 어떤 도구로, 시간 한도는)과 그 실패를 IQDebug 에 유리한 증거로 써도 되는지.
- **사용자 의견(11-17).** 같은 분기를 타더라도 입력이 다르면 산술 결과가 달라진다. 그래서 witness 와 범위 중심값은 **조건문을 파싱해 조건식의
  상수에서 경계값을 뽑는 방식**(경계값 분석)으로 정하자. 이 선택은 §0.3-3 의 B-대표 전략과 같은 것이다.
- **확정(11-17, 이 세션 제안에 사용자 동의).**
  - 같은 분기라도 입력이 다르면 값이 다르다. 그래서 B 의 핵심은 범위 실험(0.2-3)과 같다. 분기 전환은 부차적이 되고 witness 문제도 작아진다.
  - **경계값 분석을 범위 중심을 정하는 규칙으로 쓴다.** 조건식이 입력·상태와 상수의 비교(`x > 100`)이거나 다른 입력과의 비교(`amount <= balance[a]`)이면,
    AST 에서 그 상수나 비교 대상을 꺼내 범위가 경계를 걸치도록 잡는다. 솔버는 쓰지 않는다. 같은 규칙을 §0.3-3 의 B-대표 입력 선택에도 쓴다.
  - 해시, 외부 호출 반환값, 여러 변수의 비선형 결합이 들어간 조건은 이 방식으로 맞출 수 없다. 이런 경우는 **"경계 맞춤 불가"** 로 표시하고 그 수를 보고한다.

#### 0.2-5 soundness 보고 방식 (무엇을 "맞았다" 고 말할 수 있나)

- **배경.** 1차 외부 검토(P0-6): 표본 입력 몇 개에서 포함이 성립했다고 "sound 하다" 고 쓰면 과장이다. 2차 검토: 1,000 개 지점을 계산했는데 구체 실행이
  50 개 지점에만 도달했다면, "관찰된 구체 상태는 모두 포함됐다" 는 참이지만 1,000 개 지점을 검증한 것은 아니다. 여기에 이 세션의 보충: 포함 검사가
  공짜로 참이 되는 더 큰 원인은 IQDebug 값이 **⊤** 인 경우다. ⊤ 는 모든 값을 포함하므로 포함률 100% 가 아무 의미 없이 나온다.
- **현재 안.**
  - 표현 셋을 구분한다. "시험한 입력에 대한 포함", "관측된 위반"(포함 실패가 하나라도 나온 경우), "전수 검증"(정의역 전체를 실행한 경우만).
  - 분기 판정 셋을 구분한다. 구체 실행으로 도달 확인 / IQDebug 가 ⊥(도달 불가)로 판정 / 표본에서 미관측.
  - 노드 상태는 **그 지점에 실제로 도달한 구체 실행만** IQDebug 의 IN 상태와 비교한다. IQDebug 의 IN 은 그 노드로 오는 모든 경로의 합이기 때문이다.
  - 지표 둘을 항상 같이 낸다. **Observed Inclusion Rate** = 포함이 성립한 관측 / 비교 가능한 구체 관측 전체(분모 0 이면 100% 가 아니라 N/A).
    **Observation Coverage** = 구체 실행이 도달한 지점 / IQDebug 가 ⊥ 이 아니라고 판정한 착지 가능 지점. IQDebug 가 ⊥ 이라 했고 구체 실행도 도달하지
    않은 지점은 서로 일치하는 경우라 분모에서 빼고 따로 센다.
  - 한 지점을 1,000 번 지나는 실행이 비율을 좌우하지 않도록 관측 단위·지점 단위로 둘 다 보고한다.
  - **정밀도 지표를 반드시 같이 낸다.** 비교한 관측 중 IQDebug 값이 ⊤ 인 비율, ⊤ 가 아닐 때 IQDebug 구간 폭을 구체 관측값 범위와 비교한 비율.
- **남은 쟁점.** ⚑ 구간 폭 비율의 정확한 정의(구체 관측이 1 개뿐이면 범위 0 이 되는 문제), 주소·bool 처럼 구간이 아닌 값의 정밀도 표현.
- **사용자 의견(11-17).** 논문을 쓸 때 다룬다(실험 설정 결정 대상에서 뺀다). 위 "현재 안" 대로 데이터는 모아 둔다.

#### 0.2-6 보고 그룹·통계·시간 측정

- **배경.** DAppSCAN 은 프로젝트 집중도가 높다(상위 10 프로젝트가 타깃의 약 60%). 함수를 독립 표본으로 보고 평균을 내면 큰 프로젝트 몇 개가 결과를
  좌우하고 신뢰구간이 지나치게 좁게 나온다. 함수 종류마다 성공률·시간도 다를 것이다.
- **현재 안.**
  - 결과를 그룹별로 나눠 보고한다. T1 / T2 internal·private / T2 library / root·non-root / CG3 포함 여부 / 계층(실질 구조 vs 연산 계층).
  - 신뢰구간은 **프로젝트 단위 cluster bootstrap**(프로젝트를 묶음으로 재표집).
  - 시간은 cold(첫 실행, 캐시 없음)와 warm(캐시 유지)을 분리하고, 반복 실행 후 median·p95·분포를 낸다.
  - IQDebug 시간은 단계별로 쪼갠다. analyze(의존성 로드 포함) / 슬롯 도출 / evaluate / 탐색(엔진 호출 0). baseline 의 하네스 자동 생성은 별도
    setup 비용으로 둔다.
- **근거.** 단계별로 쪼개야 "IQDebug 는 분석이 느리지만 탐색은 공짜" 같은 구조가 드러나고, 어느 단계를 baseline 의 어느 단계와 맞대야 공정한지 판단할 수 있다.
- **남은 쟁점.** 반복 횟수, cold 의 정의(프로세스 재시작까지인지).
- **사용자 의견(11-17).** 0.2-5 와 마찬가지로 보류.

#### 0.2-7 대상 함수 범위 (root 만 vs 전부)

- **배경.** 사용자 고민: 다른 함수의 callee 인 함수를 빼고 호출 그래프의 root 만 대상으로 할지, 실질 타깃 전부로 할지.
- **현재 안.** 전부를 분모로 두고 함수마다 `is_root` 태그를 달아 root 부분집합을 민감도 분석으로 함께 보고하는 쪽에 기울어 있다.
- **근거.** (a) internal 함수는 거의 전부 누군가의 callee 라 root 로 한정하면 사실상 T1 만 남고 T2 가 통째로 빠진다. (b) `transfer` 처럼 내부에서도
  불리는 외부 진입점이 빠진다(원래 정책도 in-degree 0 을 쓰지 않았다). (c) callee 를 직접 디버깅하는 것도 정당한 사용 사례다. 반대 논거: callee 본문이
  caller 의 Step Into 로 한 번, 자기 타깃으로 한 번 측정돼 표본이 독립적이지 않고 큰 library 함수에 가중이 실린다 — 그래서 root 부분집합 결과를 같이 낸다.
- **덧붙임.** private 함수는 하네스(파생 컨트랙트)로도 직접 부를 수 없어 baseline 에서는 계측이나 소스 변형이 필요하다. T2 는 워크플로별 지원 여부로 기록한다.
- **남은 쟁점.** root 판별에 쓸 호출 그래프의 범위(같은 프로젝트 전체)와, 함수 포인터·`using for`·프록시 같은 간선을 어떻게 처리할지.
- **사용자 의견(11-17).** **전부로 한다.** 확정. `is_root` 태그와 root 부분집합 민감도 분석은 보조로 유지한다.

### 0.3 아직 결정하지 않은 것

#### 0.3-1 데이터셋에 맞춘 튜닝 비판에 어떻게 대응할까 ⚑

- **배경.** IQDebug 는 DAppSCAN 타깃을 분석하면서 발견한 파서·분석기 버그를 고치고 있다(§0.1-8 방침). 연구 방법으로 잘못은 아니지만, 최종 평가 데이터를
  보면서 도구를 고쳤으므로 리뷰어가 **benchmark overfitting**(평가 데이터에 맞춰 도구를 조정해 결과가 일반화되지 않는다)이라고 비판할 수 있다.
  2차 외부 검토가 "매우 중요" 로 꼽았다. 외부 검토가 낸 후보는 셋: 데이터셋 전체를 개발·평가에 쓰고 수정 이력 공개 / 일부 프로젝트를 독립 최종 검증 집합으로
  남김 / 전체에서 평가하되 별도 미사용 프로젝트로 민감도 분석. 집합을 나눈다면 파일이 아니라 **프로젝트 단위**(같은 프로젝트 파일은 import 와 코드를 공유).
- **이 세션의 판단.** 486 개 전부를 의존성 폐포 빌드로 이미 엔진에 돌렸고 89 개의 실패 원인을 다 봤으므로, 486 안에 "한 번도 안 본" 프로젝트는 없다.
  또 상위 10 프로젝트가 60% 라 어느 프로젝트를 떼느냐에 따라 검증 집합의 성격이 크게 흔들린다. 그래서 두 번째 안(486 안에서 holdout)은 성립하기 어렵다.
- **제안 조합.** (1) 고친 버그마다 **데이터셋과 무관한 최소 합성 예제 + 회귀 테스트**를 붙여 수정 목록을 공개한다 — "특정 컨트랙트에 맞춘 땜질이 아니라
  Solidity 지원의 일반적 결함" 이라는 근거. 지금까지 고친 것(여러 줄 enum 뒤 선언, 빈 블록 등)은 대부분 이 성격이다. (2) 비교 실험 전에 엔진 버전을 고정하고,
  이후 고치면 재실행 이력을 남긴다. (3) 고정 이후 486 밖의 처음 보는 소규모 프로젝트 집합으로 analyze 성공률을 한 번만 잰다.
- **결정할 것.** 위 조합을 채택할지, 데이터셋 동결 시점(버그 수정 전에 동결하고 수정 목록을 따로 남김 vs 수정을 마친 뒤 동결), (3) 의 외부 집합을 어디서 구할지.
- **사용자 의견(11-17).** 486 개가 다 평가 대상이어야 한다. 486 안에서 holdout 을 떼지 않는다. → 두 번째 안은 기각. (1)·(2)·(3) 채택 여부와 동결 시점은 미정.
  - *이 세션 권고(미확정).* (1)·(2) 를 채택하고 **버그를 다 고친 뒤** 엔진 버전을 고정한다. 고친 버그마다 합성 예제 + 회귀 테스트를 붙여 수정 목록을 공개한다.
    (3) 은 여유가 있을 때 한다.

#### 0.3-2 효과 미모델링 호출(CG3)이 있는 함수를 soundness 에서 어떻게 다룰까 ⚑

- **배경.** CG3 호출(상태 변경 외부 호출, 컨트랙트 타입 외부 호출, `call`/`delegatecall` 등)에서 IQDebug 는 반환값을 ⊤ 로 두고 피호출 쪽 효과를 모델링하지
  않는다. baseline 은 실제(또는 mock) 피호출 코드를 실행한다. 사용자 판단: IQDebug 는 전체 의미론을 다루지 않으므로 이 경계를 철저히 조사해 명시해야 한다.
- **쟁점 1 — 전제를 명시할까.** "CG3 호출은 현재 컨트랙트의 storage 를 바꾸지 않는다" 를 IQDebug 의미론의 명시적 전제로 둔다. 재진입(외부 컨트랙트가
  콜백으로 현재 컨트랙트 함수를 다시 불러 storage 를 바꾸는 것)은 이 전제 밖이다.
- **쟁점 2 — 어느 지점까지 비교할까.** 예:
  ```solidity
  function f(uint x) external {
      uint y = x + 1;              // ← CG3 이전: IQDebug 상태를 그대로 검증할 수 있다
      token.transfer(msg.sender, y); // CG3
      uint z = y * 2;              // ← CG3 이후
  }
  ```
  - (a) CG3 가 있는 함수는 통째로 soundness 집계에서 뺀다. 가장 보수적이지만 평가 지점이 많이 줄어든다.
  - (b) CFG 상 **어떤 CG3 호출 노드에서도 도달할 수 없는 지점**만 비교한다. 소스 줄 순서로 판단하면 안 된다(루프로 CG3 이후에 다시 오는 지점이 있다).
    내부 callee 안의 CG3 는 호출 지점에서 CG3 로 친다.
  - (c) 이 세션의 보충 관찰: CG3 이후 IQDebug 가 실제로 틀릴 수 있는 이유는 좁다. 반환값은 ⊤ 라 오히려 항상 sound 하고, 다른 컨트랙트의 상태는 원래 추적
    대상이 아니다. 깨지는 것은 callee 가 현재 컨트랙트 storage 를 바꾸는 경우(재진입 콜백, `delegatecall`)와 `address(this).balance` 가 바뀌는 경우뿐이다.
    그래서 정본의 외부 mock 이 콜백하지 않으면 `delegatecall`·잔액 읽기를 뺀 CG3 이후 지점도 비교할 수 있다. 다만 "전제를 시험 환경에 맞춰 놓은
    순환논증" 이라는 공격을 받을 수 있다.
- **결정할 것.** 전제 명시 여부, (a)/(b)/(c) 중 무엇을 주 집계로 하고 무엇을 보조로 할지.
- **사용자 의견(11-17).** 재진입을 고려하는 모드와 고려하지 않는 모드를 나누는 것은 별도의 큰 연구 주제다. 이번에는 **"재진입은 고려하지 않는다" 를
  전제로 두고 discussion 에 적는다.** CG3 가 있는 함수에서 soundness 는 주장하지 않는다. 다만 값 계산은 함수 끝까지 이루어진다는 점을 서술한다.
  → 쟁점 1(전제 명시)은 확정.
  - *이 세션 보충.* `delegatecall`(일반 42 + 어셈블리 13 = 55 곳)은 재진입이 없어도 현재 컨트랙트 storage 를 바꾼다. 그래서 재진입 전제만으로는
    덮이지 않으니 따로 표시해야 한다. `address(this).balance` 읽기도 같다.
  - **확정(11-17).** CG3 가 있는 함수도 **집계에서 빼지 않는다**((a) 기각). 대신 CG3 이후 값이 ⊤ 같은 의미 없는 값이 아니라는 근거를 같이 낸다.
    - *측정 지점.* 모든 문장을 비교하면 양이 많다. 그래서 주 측정 지점을 **함수 exit 상태**(storage 사후 상태 + 반환값)로 둔다. "마지막 문장" 이 아니라
      exit 으로 정의하는 이유는, 분기마다 `return` 이 있으면 마지막 문장이 하나로 정해지지 않기 때문이다. exit 은 여러 경로의 합이라 중간 지점보다 넓다.
      그래서 중간 지점 비교는 일부 함수에서만 보조로 한다.
    - *지표.* soundness(구체값이 구간에 포함)와 정밀도(⊤ 아님, 구간 폭)를 **항상 같이** 낸다(§0.2-5). CG3 이후는 ⊤ 덕분에 포함이 공짜로 성립할 수 있기 때문이다.
    - *⊤ 원인 구분.* CG3 반환값에서 파생된 변수의 ⊤ 는 정직한 결과다. 이것은 **"CG3 반환 의존 ⊤"** 로 따로 세서 정밀도 손실 ⊤ 와 섞지 않는다.
    - *실행 조건.* baseline 의 외부 mock 은 콜백하지 않는다(재진입 전제와 일치). `delegatecall` 포함 함수는 표시해서 따로 본다.
    - *남은 것.* 보조 중간 지점 비교의 대상 함수 선정, "CG3 반환 의존" 판정 방식(IQDebug 데이터 흐름으로 할지, AST 로 할지).

#### 0.3-3 표본 예산 N 의 값

- **배경.** 0.2-3 의 구성 방식은 정했지만 케이스당 N 을 얼마로 할지는 미정. 기존 계획의 사다리는 100/1,000/10,000.
- **고려 사항.** EXPERIMENT_PLAN 실측: W2 warm 단일 호출 약 0.044 초, N≤10,000 열거는 약 8 초(외삽, 소형 Vault). 상태변수에 구간을 주면 조합마다
  상태 재주입이 필요해 더 늘어나고, 큰 컨트랙트는 호출당 시간도 길다. 케이스 수가 수백~수천이면 N=10,000 은 전체로 수 시간 이상이 될 수 있다. 반대로 N 이 작으면 "표본이 작아 위반을 못 찾았다" 는 반론에 약하다.
  변수가 적은 케이스는 어차피 전수로 끝난다.
- **결정할 것.** 고정 N 하나로 갈지, 사다리(작은 N 을 전체에, 큰 N 을 부분집합에)로 갈지.
- **2026-11-17 논의 결과(사용자 승인, 세부 수치 미정).**
  1. *폭 설정.* 변수별로 범위를 다르게 잡지 않는다. 모든 입력 변수에 같은 폭 w 를 주고 w = 1..5(또는 1..10)로 올린다. 변수가 k 개면
     조합 수는 w^k 이다. 시간은 조합 수에 선형이지만 폭에 대해서는 지수로 는다. 서술할 때 이 둘을 구분한다.
  2. *baseline 시간 산정.* w^k 조합을 다 실행하지 않는다. 폭 0(구체값 하나) 실행 시간 t 를 재고 조합 수를 곱한다.
     모델은 T(n) = T_고정(anvil 기동·`forge create`·컴파일) + n·t 이다. 두 값은 따로 잰다. t 는 값 하나의 반복이 아니라 범위 안 표본(30–100개)의
     평균·분산으로 잰다. 경로마다 비용이 다르기 때문이다(revert 경로는 짧고, 루프 횟수는 입력에 따라 다르다). 조합 수 ≤ 10^4 인 설정은 실제로 전수 실행해서
     예측과 실측의 오차를 보이고, 그보다 큰 설정만 예측치로 보고한다.
  3. *예상 반론.* "개발자는 w^k 를 다 돌리지 않는다. 거의 같은 경로에 시간을 부풀렸다." 이 반론은 피하지 않고 설계에 반영해서,
     baseline 전략 셋을 함께 보고한다.
     - (B-전수) w^k × t. IQDebug 와 **같은 보장**(범위 전체의 sound 상한)을 얻는 비용이다.
     - (B-대표) 경로·경계값마다 입력 하나(0.2-4 의 조건식 상수 기반 선택). 시간은 p·t(p = 경로·경계 수)로 가장 싸다.
       같은 경로라도 입력이 다르면 산술 결과가 달라진다. 그래서 이 전략이 실제 도달 값 범위를 얼마나 덮는지(놓친 최솟값·최댓값)를 측정한다.
     - (B-동일예산) IQDebug 가 쓴 시간만큼 무작위 입력(사실상 fuzzing)을 실행하고, 관찰한 값 범위가 실제 도달 범위의 몇 %를 덮는지 본다.
       **주 공정 비교 지표**이다. "누가 빠른가" 가 아니라 "같은 시간에 누가 더 많이 아는가" 를 묻는다. 실제 도달 범위는 작은 설정의 전수 실행으로 구한다.
  4. *보고 단위.* w^k 는 초보다 **필요 실행 횟수**로 먼저 보여 준다. 초는 t 를 어떻게 쟀는지에 따라 공격받으므로 보조 지표로 둔다.
  5. *주장 수위.* t ≈ 0.044 초라서 IQDebug 실행이 1 초면 손익분기점은 실행 약 25 번이다. B-대표는 IQDebug 보다 빠를 수 있다.
     그래서 주장의 중심은 속도가 아니라 "한 번에 범위 전체를 sound 하게 덮는다" 이다. 속도는 w 가 커질 때 baseline 비용이 지수로 느는 추세로만 보인다(0.3-5 와 연결).
  - *남은 것.* w 의 상한(5 또는 10), 표본 수, 전수 실행 상한(10^4)을 확정하는 일. B-동일예산의 무작위 분포(균등 또는 경계 가중).
    ⚑ **외부 LLM 과 논의한 뒤 확정한다**(사용자 11-17).

#### 0.3-4 reachable-state 실험을 할까

- **배경.** 1차 외부 검토(P0-7): IQDebug 는 "임의의 상태에서 시작" 하므로, 실제 배포·트랜잭션 시퀀스로는 절대 도달할 수 없는 상태(예: `totalSupply` 보다
  큰 개인 잔액)를 입력으로 받을 수 있다. 그래서 constructor·initializer·트랜잭션 시퀀스로 만든 **도달 가능한 상태**에서 출발하는 실험을 따로 두자는 제안.
- **이 세션의 판단.** 방향은 맞지만 도달 가능한 상태를 만드는 것 자체가 큰 작업이고(컨트랙트마다 시퀀스 설계), 남은 일정(약 7 주)에 비해 비용이 크다.
  IQDebug 의 의미론 정의도 임의 상태 출발이다.
- **제안.** 실험은 arbitrary-state 만 하고, "도달 불가능한 상태가 입력에 섞일 수 있다" 를 위협 요소로 적는다.
- **결정할 것.** 이 제안을 채택할지.
- **사용자 의견(11-17).** multi transaction 과 contract invariant 는 전제 밖으로 둔다. IQDebug 는 **single transaction / multi contract** 위에서 동작한다고
  명시한다. reachable-state 실험은 **아마 하지 않는다.** → 제안대로 위협 요소로 적는 쪽.

#### 0.3-5 operation 적합성 테스트를 추가할까

- **배경.** 1차 외부 검토(5 절)는 operation 의미론 실험이 빠졌다고 지적했다. 실제로는 RQ1 과 D3 operation oracle(S1–S4 대칭성, frontier, WellFormed) 이
  계획에 있다(검토 프롬프트가 비교 실험만 다뤄 보이지 않았다). 다만 지금 D3 는 **구조적 성질**만 검사한다. "이 프로그램에서 이 위치에서 Step Over 하면
  저 줄에 착지해야 한다" 처럼 **operation 마다 기대 결과를 명세한 합성 프로그램 테스트**는 없다.
- **제안.** 합성 프로그램 세트(분기·루프·호출·revert 조합)에 operation 별 기대 착지점을 적어 두고 자동 비교하는 적합성 테스트를 D3 에 추가.
- **결정할 것.** 추가할지, 한다면 B1(탐색 순수 모듈 추출) 이후에 붙일지.
- **사용자 의견(11-17).** **아마 하지 않는다.** 핵심적으로 주장할 부분은 operation 적합성이 아니라 이것이다. "다른 도구들보다 준비물(artifact:
  테스트 하네스·배포 스크립트·입력 열거)이 덜 필요하면서, 범위 입력에 대한 분석을 (더 빠르게?) 할 수 있다." 속도에 대한 물음표는 §0.3-3 의
  주장 수위(손익분기점 약 25 회)와 같은 판단이다. 주장 문장의 확정은 논문 세션 소관.
